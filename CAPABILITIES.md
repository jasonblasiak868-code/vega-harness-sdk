# vega-harness-sdk — Capabilities

A minute inventory of what this kit actually does, why a prompt-and-policy harness structurally cannot do it, where each rule is enforced in the published code, which test demonstrates it, and — because honesty matters more than a good pitch — the limit of each claim.

Everything below traces to `src/vega_harness/` and `tests/`. Test counts come from STATUS.md and REVIEW.md: 115 tests in 5 files, all passing. Where a capability depends on an injected dependency that this repo does not ship, that is stated, not hidden.

**Why "structurally cannot" is a fair phrase.** A prompt-policy harness asks the model to obey rules and, at best, asks the same model to check itself. The thing being checked is the thing doing the checking: if it is wrong, or manipulated, the check is wrong too, and nothing outside the model has to agree. Every capability below moves one of three things outside the model — the authority (a human-signed commitment), the expectation (a hash frozen before any effect), or the memory (an append-only chain the model cannot rewrite). A rule held outside the model cannot be talked out of, and that is an architectural property, not a tuning result.

## 1. Conductor — deterministic workflow conduct (`conductor.py`)

| # | Capability | Why a prompt-policy harness structurally cannot offer it | Where enforced in code | Test | Honest limit |
|---|---|---|---|---|---|
| C1 | Workflow execution with **no model in the loop**: the sequencer contains no model call and no generative reasoning | A policy harness's control flow IS the model's next-token decision; it cannot guarantee determinism because the controller is the thing being controlled | Module docstring "NON-GENERATIVE by design"; `Conductor.run` is pure sequencing, gating, hashing, recording — the only callables are caller-supplied steps | `test_harness.py::ConductorTests` (all); `redteam_1_conductor.py` (all) | Models may still run INSIDE a caller-supplied step; the Conductor guarantees its own determinism, not the step's |
| C2 | **Human-only gate**: a gated step runs only against a valid commitment for exactly that step, and the step cannot dodge the gate by declaring itself ordinary | A prompt can be persuaded that this action "isn't really" the forbidden one; a code gate classifies the step from its name and verbs before it runs, with no discretion to persuade | `Step.__init__` sets `human_only` from the flag OR `humanauth.is_human_only(name)` OR any human-only verb; `run()` refuses without `commitment_check(commitment, "conductor_step:<name>") is True` | `redteam_1_conductor.py::HumanGate`: `test_a_step_cannot_dodge_the_gate_by_declaring_itself_ordinary`, `test_a_step_named_for_a_human_only_action_is_gated_too`, `test_the_checker_is_asked_about_exactly_this_step` | Classification is only as good as the jacket's human-only vocabulary; an action wired around the Conductor is outside the threat model (SECURITY.md) |
| C3 | **Single-use commitments**: one signature authorises one step once; the burn is atomic across racing processes | A policy harness's "approval" is a conversation state the model can re-read, re-interpret or replay; nothing outside the model marks it spent | `run()` calls `records.burn_commitment` → `RecordChain.append_unique("COMMITMENT_USED", ...)`; `Duplicate` → gate closes and the reuse attempt is itself recorded | `test_one_signature_authorises_one_step_once`, `test_one_signature_cannot_open_two_human_only_steps_in_one_run`, `test_a_commitment_burned_by_one_of_two_racing_runs_is_refused_to_the_other` | Single-use holds per burn chain: every gate in a deployment must share ONE chain |
| C4 | **Lesson preflight that fails closed**: once per risky-verb step, surfaced lesson ids recorded, protect-text handed to the step; a failing check stops the run | "Check your memory first" is an instruction; a model under pressure skips instructions silently, and no record shows the skip | `run()`: `self.preflight(s.verbs)` inside try; ANY exception or malformed return → `STOPPED_PREFLIGHT_FAILED`, run closed with status "stopped: lesson preflight failed" | `redteam_1_conductor.py::Preflight`: `test_a_failing_or_malformed_preflight_stops_the_run_instead_of_skipping_the_check`, `test_preflight_is_called_once_per_step_not_twice`, `test_lessons_may_arrive_as_ranked_pairs_as_the_ledger_returns_them`; positive path `test_harness.py::test_preflight_lessons_are_recorded_and_protect_text_reaches_the_step` | The preflight callable is injected (conventionally the librarian lesson ledger); the Conductor guarantees it is consulted and its failure stops the run, not that any particular lesson exists |
| C5 | **Token cap** measured per step from the canonical JSON of the context; `0` is refused at construction, never read as "unlimited"; a request's `token_cap` caps its run; the cap is checked BEFORE a human-only step's commitment is burned | A prompt-level budget ("keep it short") has no counter and no enforcement point; and a mis-set zero silently means unlimited | `est_tokens = max(1, len(canon(o))//4)`; `__init__` raises on `token_cap <= 0` or non-int; `run()` stops with `STOPPED_TOKEN_CAP` | `test_harness.py::test_token_cap_stops_the_run`; `redteam_1_conductor.py::test_token_cap_zero_does_not_mean_unlimited` | chars/4 is an ESTIMATE, not any model's tokenizer; it bounds context growth, not cost exactly |
| C6 | **Strict verification**: `verify(ctx)` must return exactly `True`; a truthy string or dict does not count; a crashing verifier has verified nothing | Asking the model "are you sure?" is asking the thing being checked to check itself; loose truthiness is exactly how a self-check passes itself | `run()`: `ok_v = verify(ctx) is True` inside try; exception → `False`; failure blocks success AND registration | `redteam_1_conductor.py::LyingVerifiers`: `test_verify_must_return_exactly_true` | The verifier is caller-supplied: the kit enforces the strictness of the verdict, not the wisdom of the check |
| C7 | **Second opinion**: when supplied, it must say `agree` is exactly `True`; a crash or disagreement blocks success, with the notes hashed into the record | A single-model harness has no second witness; a policy cannot force a dissent to be recorded rather than dropped | `run()`: `so.get("agree") is True`; exception → recorded `{"agree": False, "error": ...}`; status "failed: second opinion disagreed" | `test_second_opinion_must_say_agree_exactly_true_and_must_not_crash`; `test_harness.py::test_second_opinion_disagreement_blocks_success_and_registration` | Optional by construction — a run without a second opinion is still valid; the caller decides when council is required |
| C8 | **Chain-recorded runs**: every terminal path — success, refusal, stop, failure — appends a RUN record of hashes and verdicts, never values | A conversation transcript is rewritable by the party that holds it and mixes secrets into the record; an append-only hash chain makes tampering detectable by anyone | `_close(rec)` appends "RUN" to `RecordChain` on EVERY return path; `rec` holds `in_hash`/`out_hash`/`result_hash`, lesson ids, gate verdicts | `test_the_run_record_holds_hashes_not_values`, `test_a_credential_shaped_task_id_is_refused_by_the_chain`; tamper detection `test_a_cut_off_tail_is_caught_with_a_remembered_head`, `test_eight_conductors_running_at_once_all_record_and_the_chain_stays_valid` | Records prove sequencing and integrity, not that step outputs were semantically correct |
| C9 | **Replay that locks only on exact reproduction**: a replay never registers a new candidate; it is compared to the FIRST candidate's result hash; a locked workflow refuses further replays | A policy harness "remembers what worked" as text the model can quietly re-edit; here the memory is a hash and the comparison is exact, so a drifting workflow can never become its own baseline | `replay()`: refuses if already locked; `KeyError` if unregistered; runs with `register=False`; appends `WORKFLOW_REPLAY` with `reproduced`, `status`, both hashes | `redteam_1_conductor.py::ReplayBaseline`: `test_a_replay_that_does_not_reproduce_never_becomes_the_baseline`, `test_a_workflow_whose_own_runs_disagree_is_not_locked_by_matching_the_later_one`, `test_a_reproducing_replay_locks_and_a_locked_workflow_cannot_be_replayed_again`, `test_replaying_an_unregistered_workflow_is_refused` | Step identity includes a code hash over bytecode, so a lock does not survive a Python version change — it fails safe (refuses) rather than matching |
| C10 | **Code-identity of steps**: a different function under the same name is a different workflow | A prompt harness identifies tools by name; swapping the implementation behind the name is invisible to it | `code_hash(fn)` digests `co_code`, names, varnames, argcount and constants recursively; `Step.ident()` includes it; `workflow_id` hashes all idents | `test_a_different_function_under_the_same_name_is_a_different_workflow` | Identity covers the function's own bytecode, not the transitive closure of everything it calls |

## 2. Predicted path — pre-registered expectations (`predicted_path.py`)

| # | Capability | Why a prompt-policy harness structurally cannot offer it | Where enforced in code | Test | Honest limit |
|---|---|---|---|---|---|
| P1 | **Freeze before effect**: the expected path is hashed to the ledger BEFORE anything runs; execution requires that exact hash already frozen | A model asked "did this go as planned?" answers after seeing the outcome — hindsight is indistinguishable from prediction when both live in the same context. A hash written first cannot be re-explained | `freeze()` → validate → `PATH_FROZEN` record with `spec_hash`; `run()` refuses with "spec was not frozen first, or changed after freezing" if `_frozen()` is false | `test_harness.py::test_run_refused_when_not_frozen_changed_or_no_commitment`; `redteam_2_path_gates_pipeline.py::test_a_spec_frozen_in_another_log_is_not_frozen_here` | Freeze proves WHEN the expectation was recorded, not that it was a good expectation |
| P2 | **No parachute, no jump**: freeze refuses a side-effecting step whose named recovery is absent from the registry | "Have a rollback plan" as policy is checked, if at all, after the incident; here the jump is refused at planning time | `validate()`: `if not s.get("read_only", False)` and recovery missing/not in registry → problem "has side effects and no prepared recovery (no parachute, no jump)" → `SpecRefused` | `test_harness.py::test_no_parachute_no_jump` | The recovery callable is trusted to attempt recovery; its quality is the author's responsibility |
| P3 | **Three-outcome comparison with halt-and-recover on surprise**: ON_PATH continues; PREDICTED_ALT applies its foreseen response; anything else — including any exception in action, check or response — is OFF_PATH: halt, run recovery, record INCIDENT, keep state maintained, queue a lesson, stop later steps | A policy harness decides after the fact whether a surprise "was fine"; here the taxonomy is fixed before the run and the default is halt, not grant | `run()` loop: `matches(s["expect"], ...)` → alternatives → else `OFF_PATH`; broad `except` sets OFF_PATH with the exception name; incident records `lesson_queued: True` and returns immediately | `test_unforeseen_result_halts_recovers_and_stops_later_steps`, `test_exception_is_off_path_and_contained`, `test_foreseen_alternative_applies_its_response_and_continues`; `redteam_2::test_a_crashing_check_response_or_recovery_halts_and_is_recorded_not_raised` | A failed recovery is recorded as failed and the run halts either way — containment of the world-state depends on the recovery itself |
| P4 | **Strict descriptors, exactly one test each**: `equals` is type-strict (1 is not True), `in_range` is finite numbers and never bool, `is_true` requires the observation to BE that bool, `custom` must return exactly True; two tests or zero tests are refused at freeze | A loose predicate lets a surprise be classified as expected — the prediction equivalent of a lying verifier | `matches()` type checks throughout; `_tests_in()` + `validate()` enforce exactly one known test per descriptor | `redteam_2_path_gates_pipeline.py::Descriptors` (5 tests), `test_a_descriptor_with_two_tests_or_none_is_refused_at_freeze`, `test_a_loose_check_does_not_turn_a_surprise_into_on_path`, `test_harness.py::test_unknown_descriptor_is_refused_at_freeze` | Six descriptor kinds is a small vocabulary; richer expectations must be written as registry `custom` checks |
| P5 | **Execution under an exact-spec commitment**: running needs a human commitment for purpose `execute:<spec hash>` — not the goal, the hash — checked strictly and burned before the first action | A policy harness's approval attaches to an intention described in words; words drift. A hash cannot drift: edit one character of the spec and the commitment no longer fits | `run()`: purpose string includes `spec_hash`; `commitment_check(...) is True` inside try (crash = refuse); `burn_commitment` before the step loop; `Duplicate` → "already used" | `redteam_2::Commitments`: `test_a_signature_for_one_spec_does_not_run_another`, `test_one_signature_runs_a_spec_once`, `test_a_loose_or_crashing_checker_does_not_run_anything` | Same shared-burn-chain condition as C3 |
| P6 | **Hashed observations**: observations, response results and recovery results enter the log as digests, never as text; non-JSON observations get a type-digest instead of crashing the log | A transcript log mixes evidence with secrets and free text the writer controls; digests commit to the value without publishing it | `_digest()`; STEP records carry `obs_hash`, `response_result_hash`; incident carries `recovery_result_hash` | `test_results_enter_the_log_as_hashes_never_as_text`, `test_outputs_that_are_not_json_do_not_crash_the_log` | A hash proves consistency, not meaning: you cannot read the observation back from the log |
| P7 | **Calibration with a lower bound**: measured share of steps that held, Wilson lower bound at z=1.96, per-spec or overall | "The plan went as expected" as a vibe is unauditable; a count over frozen predictions is checkable by anyone with the log | `calibration()` counts STEP records with outcome in (ON_PATH, PREDICTED_ALT); `wilson_lower()` | `test_calibration_reports_measured_hit_rate_with_a_lower_bound`, `redteam_2::test_calibration_can_be_read_for_one_spec` | Stated in the source itself: it counts whatever was frozen and run — easy specs raise it. It measures prediction accuracy, not difficulty or plan quality |

## 6. DKG + lattice integration — the wiring, exactly as published

This section describes only what THIS repo's published code shows.

**Direct imports (real wiring).** Three, all pointing down layers:

- `records.py` imports `vega_custody.dag` — every harness record is a custody-chain entry.
- `conductor.py` imports `vega_jacket.humanauth` — human-only classification of step names and verbs.
- `use_gate.py` imports `vega_librarian.lesson_ledger` (inside `preflight`) — the lesson ledger.

**There is no direct import of `vega_dkg`, `vega_reasoning` or any galaxy module anywhere in this repo's `src/`.** The knowledge-graph and predictive-lattice integration is by **injected dependency and record convention, not by import**, and it is honest to say so plainly:

- The pipeline's knowledge-facing stages are slots with documented shapes: `deps["recall"]`, `deps["precedents"]` (stage 2 prior memory), `deps["associate"]` (stage 3 association — conventionally keyed by knowledge-graph node ids, which stage 5 sorts and hashes into the cache-stable prefix), `deps["history"]` (stage 6), `deps["kinetic"]` (stage 7, recorded in the blueprint as `lattice_prediction`), `deps["route"]` (stage 9), `deps["library_fit"]`/`deps["combine"]` (stage 10, conventionally fed by the repo-library processing side of the knowledge layer), `deps["arsenal"]` (stage 12), `deps["hybrid"]` (stage 13).
- A slot without a supplied callable returns `NOT_BUILT`, stage 14 counts it, and the blueprint lists it. Per STATUS.md, prompt reconstruction, kinetic prediction, history, arsenal and hybrid are DESIGNED ONLY in this release.
- The lattice-side foresight itself — the predictive lattice in vega-reasoning-sdk's predict.py and the galaxy view of levels, convergence and futures — lives in those repos (layers 11 and 14), which sit ABOVE this one. This kit never imports upward; the family rule is that dependencies point down only. The connection is the record format: a harness that wants lattice foresight injects it as the `kinetic`/`history`/`associate` deps, and whatever those deps return is hashed into the blueprint and the run record like any other stage output.

So: the harness is **lattice-ready by contract, not lattice-coupled by code**. Nothing in this repo fabricates graph or lattice results, and nothing silently degrades when they are absent — the absence is a named status in a chained record.

## 7. Predictive strategy from experience

The claim: this kit turns what already happened into what happens next, through four mechanisms that all leave verifiable records. Each is described exactly as the published code implements it.

**1. Lessons before action (librarian preflight).** Past incidents distil into lessons in the librarian's ledger (layer 5). Before a step that declares risky verbs runs, the Conductor calls the preflight, records which lesson ids it surfaced, and hands each lesson's protect-text into the step's context (`ctx["_preflight_<step>"]`). The experience is not a suggestion in a system prompt that the model may weigh; it is a mandatory consultation whose failure stops the run (C4), and whose occurrence is itself recorded (X1). The pipeline binds the mechanism at planning time: risky verbs found in the request are attached to exactly the steps that act on them (R5).

**2. Reproduction before reuse (replay-and-lock).** A successful run registers the workflow as a CANDIDATE — not as trusted. It becomes a locked, reusable procedure only when an independent replay reproduces the first run's result hash exactly (C9). Experience is therefore earned by demonstration, under a hash comparison nobody can argue with, and a workflow whose own runs disagree stays unlocked. The baseline is always the FIRST candidate, so drift can never ratify itself.

**3. Prediction before effect (frozen paths).** The strongest use of experience is a prediction you can be held to. Stage 16b freezes the expected path — every step's expectation, its foreseen alternatives and their responses, its recovery — to the ledger before any effect (P1, P2). Reality is then classified against the frozen text: on-path, foreseen-alternative, or surprise-halt-recover-record-lesson (P3). Calibration turns the accumulated outcomes into a measured hit rate with a confidence lower bound (P7): the system's foresight is a number anyone can recompute from the chain, not a reputation.

**4. Foresight slots above the record layer (lattice side).** The family's predictive lattice — vega-reasoning-sdk's predict.py, and the galaxy view of levels, convergence and futures — is designed to feed exactly the slots this pipeline exposes (`kinetic`, `history`, `associate`, `route`; section 6). In this release those slots report NOT_BUILT unless the caller injects the real thing. The honest statement: the harness's own predictive strategy from experience is fully built through mechanisms 1–3; the lattice-informed extension is a documented contract with a fail-honest default, and its implementation lives in the repos above this one.

The loop closes because all four mechanisms write to the same append-only chain: the lessons consulted, the candidates registered, the replays compared, the specs frozen, the outcomes classified, the incidents with `lesson_queued: True`. The next run's preflight, the next replay's baseline and the next calibration count are all read back from records the model cannot rewrite.

## 8. The five-phase verification loop, as this family position embodies it

Decompose, solve, verify, synthesize, reflect — in this architecture the loop is not a prompt pattern; each phase is a distinct piece of machinery with a record:

- **Decompose** — the request is validated (R9) and decomposed into 18 named stages, each a `Step` with declared verbs and identity (R1); candidates are decomposed further by the challenge stage, which refuses to stop at the first fit (R3). Decomposition happens before any authority is spent.
- **Solve** — the Conductor runs the steps deterministically, with the lesson preflight, token cap and human-only gate around each one (C1–C5). Solving is bounded: measured against the cap, hashed at every boundary (C8).
- **Verify** — verification is strict and external to the solver: `verify(ctx)` must return exactly True, a crashing verifier verifies nothing (C6), and an optional second opinion must agree exactly or block success (C7). On the frozen path, verification is comparison against a pre-registered expectation with a halt default (P3, P4). In the wider family, this phase is owned by vega-metacog-sdk (layer 12): evidence rungs and the completion gate — this kit's strict-verify-plus-second-opinion is the same stance applied inside a workflow, and the metacog layer is where the family keeps the dedicated owner.
- **Synthesize** — stage 17 assembles the blueprint: every stage's output, the chosen path, the unbuilt list, the frozen prediction's hash, `requires_commitment: True` (R1, R4). The synthesis is a hashed, chained artifact (X1), and the result hash of the whole run is what replay compares against (C9).
- **Reflect** — an OFF_PATH step records an INCIDENT with `lesson_queued: True` (P3): the surprise is queued as a lesson for the librarian, which distils it, which the next preflight surfaces (mechanism 1 of section 7). Calibration reflects at the aggregate level (P7). Reflection is not a mood at the end of a transcript; it is a record with a consumer.

The point of the family position: each phase has a different trust posture — decomposition is cheap and model-friendly, solving is bounded and recorded, verification is strict and external, synthesis is hashed, reflection feeds the next decomposition — and the model never holds authority at any of the seams.

## 9. Improving and deploying intelligence

The mechanisms compose into an improvement loop that runs on records, not on hopes:

1. **Lessons change future preflight behavior.** An incident queues a lesson (P3); the librarian distils it; the next run's preflight surfaces it before the risky step, with its protect-text in the step's context and its id in the record (C4). The same mistake gets harder to repeat, and the chain shows the lesson being consulted.
2. **Predicted paths get tighter.** Calibration measures which predictions held and which did not (P7). Off-path outcomes are incidents with recorded step, type and recovery result — the raw material for writing better expectations, better alternatives and better parachutes into the next spec. Because freeze refuses a spec without recoveries (P2), tightening the path and widening the safety net happen together.
3. **Surprises get rarer.** Tighter predictions plus richer alternatives move outcomes from OFF_PATH (halt, recover, incident) to ON_PATH or PREDICTED_ALT (continue with a prepared response). The hit rate is not a claim; it is a recomputable number over the chain.
4. **Human commitments are spent only where they matter.** The human-only classification (C2) decides where a signature is required at all; the exact-action, exact-spec-hash, single-use burn (C3, P5) makes each signature small and specific. As workflows lock through reproduction (C9), the locked procedures carry the verified shape of past success — and the human's scarce attention goes to the new, the risky and the unreproduced, instead of rubber-stamping the routine. The whitepaper's worry — a human bottleneck who stops reading and clicks yes — is answered by making each approval specific, single-use and recorded, so careless approval is harder and every approval is attributable.

Deploying, honestly: this is a reference implementation. The improvement loop is real code with real tests, but it is not hardened for production, has not been independently security-reviewed, and its stages that depend on unbuilt or un-injected components say NOT_BUILT until someone supplies them. Deploying intelligence with this kit means wiring the deps, sharing one burn chain across every gate, verifying the chain on a schedule, and keeping a human who reads what they sign.

## 10. A category of its own

Most harnesses govern the model from inside the model: system prompts, policy text, self-checks, tool descriptions — all enforced by the thing they constrain, all leaving records only that thing controls. This kit is built on the opposite stance, and the difference is architectural rather than a matter of degree:

- **Governance-first: authority lives outside the model.** The only source of authority is a human signature the model never holds; every gate checks it strictly and burns it on use (C2, C3, X4). A rule held outside the model cannot be replicated by prompt-level policy, because prompt-level policy is, by construction, inside the model — this is the family's founding argument, and this kit is where it meets workflow execution.
- **A deterministic conductor.** The control flow contains no model call (C1). The model reasons inside steps; the sequencing, gating, measuring and recording cannot be persuaded.
- **Pre-registered predicted paths.** Expectations are hashed to a ledger before effects, compared strictly against reality, and default to halt-and-recover on surprise (P1–P5). Hindsight cannot masquerade as foresight when foresight has a timestamp and a hash.
- **Single-use human commitments.** One signature, one exact action, once — for the step and, separately, for the exact frozen spec (C3, P5, R2). Approval is spent, not shared.
- **Chain-of-custody by default.** Every run, gate verdict, freeze, step outcome, incident and burn lands in one append-only hash chain holding hashes rather than secrets (C8, X1, X5). Verification does not require trusting the model, the operator or this project.
- **Lattice-informed foresight, wired by contract.** The pipeline exposes named, fail-honest slots for the family's knowledge graph and predictive lattice (sections 6–7): built mechanisms consume real experience today — lessons, reproduction, calibration — and the slots above them report NOT_BUILT rather than pretending.

None of these is a smarter prompt. Each is a place where the architecture holds something — authority, expectation, memory — that no prompt inside a model can hold, because a prompt can always be outweighed by the next token. That is the category: conduct you can verify without trusting the conductor.
